# Technical writing portfolio readiness

This page maps the documentation portfolio to common technical-writing requirements. It is an evidence plan, not a guarantee of selection.

| Employer requirement | Evidence in version 0.1 | Remaining proof |
| --- | --- | --- |
| Clear technical English | Tutorial, explanations, reference and troubleshooting pages | Independent editorial review |
| Documentation structure | Diátaxis-style content separation | Publish navigation in a docs site |
| Docs as code | Markdown repository structure, contribution workflow and changelog | Public Git history, branch and pull request |
| Git and Markdown | Repository-ready Markdown | Commit, review and merge the pages in GitHub |
| Product documentation | Architecture, authentication, tool reference and support guidance | Verify each page against the deployed application |
| Information architecture | Organised entry points and content types | Add search and test navigation with users |
| API documentation | Boundary and definition of done recorded | Build working demo API, OpenAPI specification and examples |
| API and command-line testing | Testing requirements defined | Run Postman and `curl`; publish results |
| Read source code | Documentation derived from component and service descriptions | Review actual React, JavaScript and one small Python Lambda implementation |
| Technical accuracy | Known limitations and verification matrix | Complete verification and authoritative source checks |

## When to apply

The current pack is enough to strengthen content-led and product-documentation applications. For roles with API documentation as a core requirement, complete the demonstration API milestone first.

Do not wait until every one of the 26 product tools has a guide. A smaller set of accurate, tested and maintained pages is stronger evidence than a large unverified library.
